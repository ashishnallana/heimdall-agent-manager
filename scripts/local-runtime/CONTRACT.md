# Local runtime launcher contract

`scripts/local-hub.sh` and `scripts/local-bridge.sh` implement this contract on Linux and macOS. `local-hub.ps1` and `local-bridge.ps1` must implement the same contract on Windows, and the preview integration must read it, not reimplement it. This file is the source of truth. Where a launcher and this file disagree, fix the launcher.

## Commands

| Script | Verbs | Options that must behave identically |
|---|---|---|
| `local-hub` | `start`, `stop`, `status`, `approve-device`, `help` | `--name`, `--hub-port`, `--proxy-port`, `--ui-port`, `--user`, `--build nix\|odin\|none`, `--bin-dir`, `--no-ui`, `--no-seed`, `--no-plan-limits`, `--code` |
| `local-bridge` | `start`, `enroll`, `stop`, `status`, `help` | `--name`, `--hub-url`, `--hub <hub-instance>`, `--port`, `--local-endpoint-port`, `--auto-enroll`, `--user`, `--build`, `--bin-dir`, `--pty-host-bin` |

PowerShell spells the options the same way (`-Name` aliases are optional). Exit code 0 means success, and anything else means the launcher refused or failed. The reason goes on stderr.

## State layout

The state root is `$HEIMDALL_LOCAL_STATE_ROOT`. When that is unset, it is `${XDG_STATE_HOME:-~/.local/state}/heimdall-local`, and on Windows `%LOCALAPPDATA%\heimdall-local`. It is never inside a checkout and never the installed `~/.local/share/heimdall`.

```
<root>/hubs/<name>/
  instance.env      KEY=VALUE record (below)
  hub.db            the hub database (plus -wal/-shm)
  seed.json         seed record: {"version":1,"seeded":{"<fixture-key>":"<id>"}}
  seed-<user>.json  the same record for each seeded paid account (see Accounts)
  approver/         device.json: the seed approver's PKCS#8 keys (0700 dir, file 0600);
                    users/<user>/device.json: each seeded account's own approver
  bin/              build outputs (nix result-* links or odin binaries)
  logs/             hub.log dev-proxy.log ui.log
  run/<svc>.pid     process records: hub proxy ui
  xdg/              private XDG_DATA/CONFIG/STATE_HOME + HEIMDALL_HOME for hub & proxy
<root>/bridges/<name>/
  instance.env
  config.toml       generated by bridge-config.mjs; enrollment adds daemon_id
  credentials/      bridge-token + bridge-token.refresh (0700 dir, files 0600)
  data/             bridge data_dir (provider_paths.json, caches, artifacts)
  agent-runs/       agent working directories
  endpoint/         --local-run-dir (local endpoint sockets)
  home/             isolated provider home (HOME of the bridge and its agents);
                    .heimdall-home-manifest.json lists every seeded file
  bin/ logs/ run/bridge.pid enroll-bin/ (logs/enroll-shims.log records intercepted service calls)
```

Instance names match `^[a-z0-9][a-z0-9-]{0,39}$`.

## `instance.env` keys

The file has one `KEY=VALUE` per line with no quoting. Write it atomically: write a temporary file, then rename it.

- **Hub:** `KIND=hub NAME HUB_PORT PROXY_PORT UI_PORT HUB_URL PROXY_URL UI_URL UI_ORIGIN PUBLIC_ORIGIN DEV_USER APPROVER_KEY CHECKOUT`. `UI_URL` is always the local Vite URL, and `UI_ORIGIN` (the origin the hub trusts for CSRF) equals it; `PUBLIC_ORIGIN` is trusted by the dev proxy only (see Public origin).
- **Bridge:** `KIND=bridge NAME HUB_URL HUB_NAME BRIDGE_PORT LOCAL_ENDPOINT_PORT CONFIG TOKEN_FILE CHECKOUT ISOLATED_HOME PROVIDERS HOME_DIR`. `ISOLATED_HOME` is `1` (provider home under `home/`) or `0` (real `HOME`); a record without it was made before isolation existed and means `0`. `HOME_DIR` is the HOME the bridge runs with.

The preview integration finds a hub's UI, proxy and API URLs here. Ports are recorded on the first start and reused after that. An explicit port that differs from the recorded one is refused, and so is a bridge `--hub-url` that differs from the one it was enrolled with.

## Public origin (reverse proxies, Heimdall preview)

The hub accepts state-changing browser requests from exactly one origin (`--ui-origin`, enforced by `csrf_decide`), and that is always the local UI (`http://127.0.0.1:<ui-port>`). Browsers do not hold a hub session: the dev proxy signs in for them and sends `Origin: <ui-origin>` to the hub itself, but only for a trusted browser origin (docs/auth-oidc.md, "Local development"). Loopback origins are always trusted. The Heimdall preview needs nothing here: `scripts/dev-preview.sh` and `scripts/ui-preview.sh` relays forward the preview origin as their own loopback origin. Any other reverse proxy, which makes the browser send its own origin, needs `--public-origin <scheme://host[:port]>` (no path; a `/p/<session>/` prefix is not part of an origin). The proxy gets it as `--trusted-origin`. It is recorded as `PUBLIC_ORIGIN` and reused on restart; an explicit value replaces it and `--public-origin local` clears it. It is not a collision resource. The local `UI_URL` keeps working alongside it, cookie WebSockets included.

The hub also gets `--pairing-hub-origins <hub-url>,<proxy-url>,<ui-url>[,<public-origin>]`, so a browser on either origin accepts bridges that paired against the hub API URL, and browsers that paired on the other origin.

## Ports

Before anything is built or started, refuse a port that:

- is outside 1024–65535,
- is given for two services,
- appears in **another** instance's `instance.env` under any `*_PORT` key, even if that instance is stopped, or
- accepts a TCP connection on 127.0.0.1.

Everything binds 127.0.0.1 only.

## Processes and ownership

A record is `run/<svc>.pid` containing `<pid> <start-time>`. The start time is `ps -o lstart=` with spaces replaced by `_`. On Windows it is the process `StartTime` in ISO-8601 form. A process is owned only when it is alive and its current start time equals the recorded one.

`stop` signals owned processes only: TERM to the process group, then KILL after 6s. It never matches by name or command line, and it never touches the installed hub, bridge or service units. Services start detached in their own session (`setsid`) so that `stop` reaches their children, such as Vite's esbuild. On Windows, use a Job Object or `taskkill /T` on the owned PID.

A launcher holds `<instance>/.lock/` (created with `mkdir`, holder PID inside) for the length of a command. A lock whose holder is dead is reclaimed.

## Hub start order

0. Mock OIDC provider (DEV ONLY; users authenticate only with OIDC): `python3 tools/mock-oidc/mock_oidc.py --port <oidc> --username <user>` (service `oidc`, port key `OIDC_PORT`, default 18090). Ready when `<issuer>jwks/` answers, issuer `http://127.0.0.1:<oidc>/application/o/heimdall-native/`.
1. Hub with the mock's environment (`HAM_OIDC_ALLOW_INSECURE_LOCALHOST=1`, `HAM_OIDC_ISSUER=<issuer>`, `HAM_OIDC_JWKS_URL=<issuer>jwks/`, `HAM_OIDC_USERINFO_URL=<issuer>userinfo/`, `HAM_OIDC_AUTHORIZE_URL=<issuer>authorize/`, `HAM_OIDC_TOKEN_URL=<issuer>token/`, `HAM_OIDC_END_SESSION_URL=<issuer>end-session/`, `HAM_OIDC_API_AUDIENCE=heimdall-api`, `HAM_OIDC_API_SCOPE=heimdall.api`, `HAM_OIDC_WEB_CLIENT_ID=heimdall-web`, `HAM_AUTO_PROVISION_USERS=true`, `HAM_OIDC_CLAIM_EXISTING_USERS=true`), `--db <dir>/hub.db`, `--migrations-dir <checkout>/src/hub/repository/sqlite/migrations`, `--ui-origin http://127.0.0.1:<ui-port>`, `--pairing-hub-origins` (see Public origin) and `--billing-enforce-plan-limits true` (`false` with `--no-plan-limits`). Health is `/api/v1/health`.
2. `ham-dev-proxy --listen 127.0.0.1:<proxy> --hub-url <hub> --default-user <user> --hub-ui-origin <ui-origin> [--trusted-origin <public-origin>]`. Requests that carry their own cookie or bearer (seeding, the approver) are forwarded unchanged. A browser from a trusted origin gets a hub session the proxy obtained through the real OIDC flow against the mock, for the selected user (`login_hint`). The browser never sees that session.
3. Seed: `node scripts/local-runtime/seed.mjs --api <proxy-url> --record <dir>/seed.json`, then the seed approver (below): `approver.mjs init`. Exit 3 from `init` means the vault was already rooted by another device; warn and continue. Then seed each paid account (see Accounts).
4. UI: `vite <checkout> --host 127.0.0.1 --port <ui> --strictPort` with `HEIMDALL_DEV_PROXY_URL=<proxy-url>` and `HEIMDALL_HUB_API_URL=<hub-url>`. If `node_modules` is missing, run `npm ci --legacy-peer-deps` first.

If any step fails, stop what has already started and exit non-zero.

## Seeding (`seed.mjs`, shared)

Seeding goes through the public REST API behind the dev proxy, signed in like a browser (the real OIDC flow against the mock; `--user` picks the account) and sending `Origin: $HEIMDALL_LOCAL_UI_ORIGIN` (the hub's `--ui-origin`) for the CSRF check:

- `POST /api/v1/agents`: definitions only, nothing is launched.
- `POST /api/v1/task-chains` without `coordinator_agent_id`, then tasks with `POST .../tasks`.
- `POST /api/v1/memories`, then `.../approve`.

A fixture is skipped when `seed.json` records its key, or when an item with the same name or title exists. Existing items are adopted into the record. Nothing is ever updated, so user edits, renames and deletions survive a restart. The script prints `seed: N created, M skipped`.

## Accounts

The dev proxy's default user (`--user`) stays on the free plan. Each seeded paid account (today `paid` on `hobbyist`; it must be in the dev proxy's default roster) gets, in order:

1. `seed.mjs --api <proxy-url> --record <dir>/seed-<user>.json --user <user>`. Its first request creates the account.
2. `node scripts/local-runtime/plans.mjs --db <dir>/hub.db --user <user> --plan <plan>`. It sets `account_billing.plan_id` with status `custom` (`free` resets to the default). This is the only direct database write, because no payment provider runs locally. The hub picks it up within its 30s entitlement cache.
3. `approver.mjs init --key <dir>/approver/users/<user>/device.json --user <user>`. Exit 3 means: warn and continue.

`--no-seed` skips all three. The browser switches accounts with `/_dev/login?user=<user>`. `local-bridge --hub <name> --auto-enroll --user <user>` approves with that account's approver, so the bridge belongs to that user.

## Bridge

- **Config.** `node scripts/local-runtime/bridge-config.mjs --template <checkout>/config.toml --out <dir>/config.toml --dir <dir> --hub-url <url> --port <port> --name <name>` rewrites `data_dir`, `credentials_path`, `agent_run_dir`, `tmux_session`, `[wrapper].daemon_url` (this bridge) and `[ctl].daemon_url` (the hub). It drops `[[peer]]` blocks and keeps an enrolled `daemon_id`.
- **Enrollment.** Only the supported device flow is used: `ham-bridge enroll --hub <url> --headless --config <cfg> --bridge-token-file <dir>/credentials/bridge-token`. Pairing is hub-blind: the hub cannot approve a bridge, a trusted vault device of the hub's user must sign the approval and unseal the keyring to the enrolling process. The bridge prints (src/bridge/enroll_device_flow.odin, "Enroll this machine") an indented approval URL ending in `/api/v1/device/add` and, after `and type this pairing code once:`, the pairing code alone on an indented line: 14 symbols of `A-Z2-7` grouped `XXXX-XXXX-XXXX-XX` (src/lib/vault/pairing.odin). Match both lines with those patterns (bash: `lr_enroll_prompt`), never by the surrounding prose.
  - Without `--auto-enroll`, show the URL and code and wait for `ham-bridge enroll` to exit; a human approves on that hub's UI.
  - With `--auto-enroll` and `--hub <name>` whose `APPROVER_KEY` exists, run `approver.mjs bridge --api <proxy-url> --key <APPROVER_KEY> --code <code> --label local-<name>`, then wait for `ham-bridge enroll` (it prints `bridge enroll SUCCESS`). Without a seed approver fall back to the human path.
  - **`ham-bridge enroll` ends by restarting the installed bridge service** (`systemctl --user restart heimdall-bridge`, `sv`, or `launchctl`). Launchers must put no-op `systemctl`/`sv`/`launchctl` shims first on `PATH`, and unset `PREFIX`, for the enroll process only. Windows has no such call.
- **Seed approver (`approver.mjs`, shared).** Run with `node --import <checkout>/tests/helpers/vaultEndpointHarness.ts scripts/local-runtime/approver.mjs <init|bridge|device> --api <proxy-url> --key <hub>/approver/device.json [--code C] [--label L] [--user U]` (`--user` signs in as that account through the mock OIDC provider, so it acts for that account and needs that account's key; requests carry `Origin: $HEIMDALL_LOCAL_UI_ORIGIN`) from the checkout (needs `node_modules`, for esbuild). It uses the UI's vault modules and the public API only (`/vault/directory/genesis`, `/device/pair-salts`, `/device/verify`, `/device/approve`, `/bridges/<id>/unseal`, `/vault/devices/<id>/approve`); it never writes the database. `init` creates the vault genesis once and is idempotent (`kept`). `device` approves a browser's pairing code from the UI, because on a seeded hub the browser joins the vault as a second device rather than being its root. Exit 0 success, 3 vault rooted by another device, 1 anything else. The key file is the local hub's account root: keep it in the instance directory, never copy it.
- **Run.** `HEIMDALL_HAM_CTL_BIN=<ham-ctl> HEIMDALL_BRIDGE_PTY_HOST=1 HEIMDALL_HAM_PTY_HOST_BIN=<pty-host> ham-bridge --config <cfg> --bind-host 127.0.0.1 --port <p> --hub <url> --bridge-token-file <tok> --local-endpoint-port <ep> --local-run-dir <dir>/endpoint`. It is ready when `bridge hub runtime ready` appears in its log.
- **Providers.** Providers are real installed CLIs on `PATH`, discovered by the bridge's own probe when the hub requests it, and recorded in `data/bridge/provider_paths.json`.
- **Provider home.** On Linux a new instance is isolated (`ISOLATED_HOME=1`) unless `--shared-home` is passed. On macOS it is shared unless `--isolated-home` is passed, because the login-Keychain sign-ins (vault keyring, Claude OAuth) have not been verified with a moved HOME. In both cases the mode is fixed when the instance is created, and an explicit flag that contradicts the record is refused (use a new `--name`): the bridge's identity file lives under the HOME it ran with. An isolated bridge, its `enroll` and everything it starts (agents, model discovery, extension installs) run with `HOME=<dir>/home`, `XDG_CONFIG_HOME`/`XDG_DATA_HOME`/`XDG_STATE_HOME`/`XDG_CACHE_HOME` inside it, and `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `GEMINI_CONFIG_DIR`, `HEIMDALL_HOME` unset; `PATH`, `SSH_AUTH_SOCK` and credential env (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN`, `OPENAI_API_KEY`) pass through. `bridge-config.mjs --fs-root <real HOME>` keeps the directory picker on the real home. Before the first start, `node scripts/local-runtime/provider-home.mjs seed --real-home <HOME> --home <dir>/home --providers <list> --trust-root <dir>/endpoint --trust-root <dir>/agent-runs` copies (0600) the providers' sign-in, onboarding/consent state and project trust, and nothing else:
  - claude: `.claude/.credentials.json`; `.claude.json` filtered to account/onboarding/consent keys plus `projects[<path>].hasTrustDialogAccepted`; `.claude/settings.json` without `enabledPlugins`, `extraKnownMarketplaces`, `hooks`, `mcpServers` or `statusLine` (which keeps `skipDangerousModePermissionPrompt`); `.claude/CLAUDE.md`.
  - codex: `.codex/auth.json`; `.codex/config.toml` without `[plugins.*]`, `[marketplaces.*]`, `[hooks]`/`[hooks.*]`, `[mcp_servers.*]` or the top-level `notify` (which keeps `[projects."<path>"] trust_level`); `.codex/AGENTS.md`.
  - gemini / antigravity: `.gemini/{oauth_creds.json,google_accounts.json,*.md}`, `.gemini/antigravity-cli/antigravity-oauth-token`; `.gemini/settings.json`, `.gemini/config/config.json` (also under `userSettings`) and `.gemini/antigravity-cli/settings.json` (keeps `trustedWorkspaces`/`permissions`) without `mcpServers`, `mcp`, `hooks`, `hooksConfig`, `extensions`, `plugins`, `toolDiscoveryCommand`, `toolCallCommand`, `tools.discoveryCommand`, `tools.callCommand`. Not `hooks.json`.
  - pi: `.pi/agent/auth.json`; `.pi/agent/settings.json` without `packages`/`extensions`. Not `extensions/`.
  - git: `.gitconfig`, `.config/git/{config,ignore}`, `.git-credentials`, `.config/gh/{hosts.yml,config.yml}`.
  Nothing that runs code on the real side (plugins, hooks, MCP servers, status-line or notify commands) is copied; the instance keeps its own on reseed. A symlink is recreated only when its target is in `/nix/store` or not writable (home-manager files); any other link is copied, so the instance cannot write back through it. Every file is listed with source path and both SHA-256s in `home/.heimdall-home-manifest.json`. `local-bridge.sh reseed-auth` re-runs the seed: real values are applied again and the instance's own plugin entries and project trust are kept. The real home is only read. This copy is the one sanctioned exception to "never copy provider tokens": local instances only, opt-out with `--shared-home`. A provider that rotates its OAuth refresh token on use can end the real session (or the copy's); sign in again and reseed. Never copy installed bridge credentials or keyrings.

## Known shared paths

These paths are keyed, so separate instances do not collide in them:

- `~/.config/heimdall/locks/` holds bridge instance locks, keyed by config path and by hub plus bridge id (under `home/` for an isolated instance).
- `~/.config/heimdall/bridges/<bridge-id>/` holds the bridge identity, keyed by the bridge id that enrollment mints (under `home/` for an isolated instance).
- The vault keyring is per OS user, not per HOME: the Linux `@u` key `heimdall:vault_keyring:<bridge-id>` and the macOS login Keychain. It is keyed by bridge id.
- `<checkout>/node_modules/.vite` is the Vite dependency cache, shared by UIs from the same checkout. It is only a cache.

### Approval links through a preview

`--public-origin` remains an origin-only setting and does not include the
`/p/<session>/` preview prefix. To print a usable enrollment link when the UI
runs under that prefix, pass the full browser base explicitly:

```bash
scripts/local-bridge.sh enroll --name example --hub plans \
  --approval-base-url https://preview.example/p/sh_123/
# Direct binary:
ham-bridge enroll --hub http://127.0.0.1:18181 --headless \
  --approval-base-url https://preview.example/p/sh_123/
```

The bridge validates an HTTP(S) base with no credentials, query, or fragment,
normalizes trailing slashes, and prints
`https://preview.example/p/sh_123/api/v1/device/add`. The local launcher records
`APPROVAL_BASE_URL` in its own bridge `instance.env` and reuses it on later
enrollments. It changes only the approval link (and the page opened for it),
never the hub API address, CSRF origin, or pairing origin. Supply a new value
when the preview session changes. The hub's origin-only verification URL stays
the default when no override is given.
