# Hub telemetry (Prometheus + Grafana)

Deployment files for scraping `ham-hub` and the host it runs on. The hub side
is `src/lib/metrics` (exposition) + `--metrics-addr` (private listener); see
`SELF_HOSTING.md` § "Hub telemetry" for the operator walkthrough.

Not to be confused with `../telegraf.conf.template`, which is the **bridge**
side (Telegraf on the customer machine, toggled by `telemetry_enabled`).

| File | Purpose | Validated with |
|---|---|---|
| `prometheus-scrape.yml` | Stand-alone `prometheus.yml` (hub, node_exporter, blackbox) | `promtool check config` |
| `alerts.yml` | Alert rules from the plan's section 7 | `promtool check rules` |
| `nixos-telemetry.nix` | NixOS module: Prometheus (15 d + 8 GB cap), node + blackbox exporters, Grafana with Authentik OIDC, nginx vhost; `logs.enable` adds VictoriaLogs (127.0.0.1:9428, 15 d), `services.journald.upload` → VictoriaLogs, the Grafana datasource plugin | `nix-instantiate --eval` against `<nixpkgs/nixos>` |
| `grafana/provisioning/` | Datasource + dashboard provider | — |
| `grafana/dashboards/{hub-health,fleet,streams,bridge-events,hub-db}.json` | **Hub Health**, **Fleet** (owner/bridge variables via the `bridge_info` join; *Bridge errors* and *Tickets* rows), **Streams & Shells**, **Bridge Events** (bridge_id/level/code variables; counters from Prometheus, event stream from VictoriaLogs), **Hub DB** (phase-1 DB latency/lock telemetry, see below) | generated by `grafana/gen_dashboards.py`; `verify-db-dashboard.sh` checks reproducibility, structure, metrics/labels against `src/` and PromQL syntax |
| `grafana/dashboards/task-system-v2.json` | **Tickets** (file name kept for existing links) | hand-maintained |
| `grafana/provisioning/datasources/victorialogs.yml` | VictoriaLogs datasource (plugin `victoriametrics-logs-datasource`); provisioned only with `logs.enable` | — |

## Hub DB dashboard (`heimdall-hub-db`)

Panels for the phase-1 DB telemetry in `docs/reference/db-telemetry.md`: lock wait/hold
percentiles, contention and waiters, per-connection execution, transactions, the
disjoint request DB components (ratio of sums), top call sites, errors, cache and
library version. Every query is scoped by the `job` and `instance` variables (one hub
at a time). Nothing uses `or vector(0)`, so a hub with `HEIMDALL_DB_TELEMETRY=off`, or
one running a build older than the telemetry, shows *No data* rather than zeros.
`busy_wait` is hidden because phase 1 always reports it as 0. The dashboard's first
row explains how to read it. All generated dashboards link to each other through the
*Heimdall dashboards* dropdown (tag `heimdall`).

The queries pass `promtool check rules` and are checked against the metric
registrations in `src/`. They have **not** been run against a live Prometheus.

### Activating it on a deployment

Pushing this repository does not update a running Grafana:

- **NixOS module** (`nixos-telemetry.nix`): the dashboard provider reads
  `${telemetryDir}/grafana/dashboards`. With `telemetryDir = "${inputs.heimdall}/tools/telemetry/hub"`
  (the setup in `SELF_HOSTING.md`), that is a Nix store copy of the flake input. To load
  `hub-db.json`, bump the host flake's `heimdall` input to a commit that contains it and run
  `nixos-rebuild switch`. Grafana then provisions it into the *Heimdall* folder. Because
  `allowUiUpdates = false`, UI edits are not saved; change the generator instead.
- **Other distros:** copy `grafana/dashboards/*.json` to the provider path
  (`/etc/grafana/dashboards/heimdall` in `provisioning/dashboards/heimdall.yml`). The file
  provider rescans every 60 s.
- **Data:** panels fill only once the hub runs a build with the DB telemetry (`basic` by
  default) and Prometheus scrapes it as `job="heimdall-hub"`.

**Host dashboard:** use the stock node_exporter dashboard, Grafana.com ID
**1860** ("Node Exporter Full"), imported against the `Prometheus` datasource.


## Quick checks

```bash
# the hub, locally
ham-hub --db /tmp/h.db --migrations-dir src/hub/repository/sqlite/migrations \
        --metrics-addr 127.0.0.1:9464 &
curl -s http://127.0.0.1:9464/metrics | nix-shell -p prometheus.cli --run 'promtool check metrics'

# the deployment files
nix-shell -p prometheus.cli --run 'promtool check rules tools/telemetry/hub/alerts.yml'
nix-shell -p prometheus.cli --run 'promtool check config tools/telemetry/hub/prometheus-scrape.yml'
```

## Bridge error events (log backend, optional)

Bridges relay enum-coded warn/error events over the bridge WebSocket; the hub
counts them (`heimdall_bridge_errors_total{code,level}`,
`heimdall_bridge_errors_by_bridge_total{bridge_id}`), stores them in SQLite for
the owner UI/API, and — when started with `--log-push-url http://127.0.0.1:9428`
— pushes each committed batch to VictoriaLogs via the Loki push API. Streams
are `{job="heimdall-bridge", level}` only; `bridge_id`, `code`, `version`,
`count` and the typed fields are structured metadata, so LogsQL filters are
field filters:

```
{job="heimdall-bridge"} bridge_id:"brg_…" code:~"agent_.*|provider_.*"
_SYSTEMD_UNIT:"heimdall-hub.service"            # the hub's own journal (journald upload)
```

`owner` is never shipped; map `bridge_id → owner` in Grafana through
`heimdall_bridge_info` (Fleet dashboard) as for every other per-bridge series.

Quick local check without Nix:

```bash
nix-shell -p victorialogs --run 'victoria-logs -storageDataPath=/tmp/vl -httpListenAddr=127.0.0.1:9428 -retentionPeriod=15d' &
ham-hub ... --metrics-addr 127.0.0.1:9464 --log-push-url http://127.0.0.1:9428
curl -s 'http://127.0.0.1:9428/select/logsql/query' --data-urlencode 'query={job="heimdall-bridge"}' | head
```

## Security notes

- `/metrics` is served only on `--metrics-addr`; it is never routed on the
  public port (non-`/api/v1` paths 404 there). Keep it on loopback: once M2
  ships, `heimdall_bridge_info{owner=...}` carries user ids (often e-mails).
- Prometheus, Grafana and both exporters bind `127.0.0.1`. Grafana is the only
  thing exposed, through nginx, and only to members of the Authentik group
  `heimdall-admins` (policy at Authentik **and** `role_attribute_strict` in
  Grafana).
- Redact `owner` in any Alertmanager template that leaves the host.
