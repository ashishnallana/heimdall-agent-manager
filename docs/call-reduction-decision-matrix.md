### Measurement boundaries

- **HTTP counts are modeled triggers, not observed network requests.** Values 92 shell registrations, 30 vault touches, 21 reads and 30 comments echo the production W40 volumes solely to size the scenarios. Those production calls are not known to have repeated identical values. The synthetic repeated-state cases demonstrate an upper bound on removable work, not a production duplicate rate.
- Repository components measure only the named component. Read detail rows omit HTTP authentication, response encoding, ownership checks outside that component, and detail enrichment. The auth user lookup is measured separately; do not sum every table row as a single traffic trace.
- The comment scenario calls the **actual `comment_task`**, with a real taskv2 engine and real UoW factory. It omits the attention projector, agent-instance authentication, and handler response author lookup. Conversation reads call `mark_read_with_receipts`; explicit-ID reads call `mark_messages_read_by_ids`. Bridge heartbeat, offline and vault-status scenarios call their real services. Vault touch uses the real repository on its dedicated write connection, without signature verification or directory response reads.
- The search scenario calls the **actual HTTP `enrich_chain_list_items` helper**, with zero chains and wired content/taskchain services; it is not an entire HTTP handler invocation. It measures precisely the unnecessary enrichment subset of an empty delta.
- **Writes means executed INSERT/UPDATE/DELETE statements**, including an UPSERT that ends up preserving all values, or a DELETE matching zero rows. It is not changed-row count, WAL frames, fsyncs, or disk writes. Trigger VM work is included in SQLite VM steps; trigger-internal statements are not independent wrapper execution counts. BEGIN/COMMIT are explicit statements; ordinary autocommit transactions are not reported as explicit COMMITs.
- **Cache page write** separately reports `SQLITE_DBSTATUS_CACHE_WRITE` from the existing cache collector. It counts SQLite page-cache writebacks (including trigger/index work), not physical-device writes or fsyncs. An equal-value UPDATE may have zero page writes or may still dirty indexes/FTS; this distinction materially changes priorities.
- The first scan pass follows closing/reopening the main connection: initially cold **SQLite connection page cache**, with an uncontrolled/warm OS cache. The second pass reuses that connection and reports zero cache misses. Scenarios in each pass share the cache; only the start of pass 0 is cold. There was no privileged OS-cache dropping and no latency or production impact claim.

### Fixture assumptions

The fixture contains 600 shell sessions (200 each run/shell/server; 30 live, spread across 20 bridge IDs), 20 bridge rows, 60 conversations with 100 incoming messages each (6,000 messages), 30 chains with 20 tasks each (600 tasks), 30 running workflow executions and 570 internal dependencies, 400 enrollment-scope tokens (20 unrevoked), one device directory and approved device, one card and one agent identity. All messages use fixed synthetic bodies and timestamps. Shell/task/message sizes are intentionally small; these counts represent a medium installation, not a sampled production database. Workflow parents are seeded before generated tasks to satisfy migration 099's owned-running-execution guard; dependencies are internal to one workflow execution, not ordinary ticket dependencies.

Fixed clocks and deterministic unique comment IDs make state-repeat tests reproducible. Assertions verify shell/bridge row equality before and after repeated identical writes, first-read receipts (100) followed by zero receipts, 30 distinct saved comments, valid result counts after index trials, and nonzero telemetry. Changing fixture distribution, SQLite version or migrations can change VM/cache numbers. Re-run for every downstream implementation.

## Ranked decision matrix for tasks 2–5

Ranking combines production slow-write priority with locally demonstrated work reduction. Vault touch remains the first production write investigation: the original report attributes 0.6–2s individual calls to it despite small VM counts. VM work is not a proxy for writer-lock, WAL or saturated-storage latency. Search is the clearest semantics-preserving local read reduction; it does not displace vault investigation. Production latency remains confounded by host I/O saturation and two unclean reboots in the original assessment. This report supplies call/statement/VM economics only.

**Write priority refinement:** same-value shell UPSERTs produce **92 page writebacks for 92 calls** despite an unchanged stored row. Already-read conversation calls produce **80 page writebacks for 20 calls** even with a fixed clock, and explicit already-read ID calls produce **141 for 20 calls**. Conversation and message FTS triggers fire on every UPDATE (`R/migrations/030_search_fts_all.sql:16`, `031_search_fts_messages.sql:19`) and delete/reinsert indexed content even when only read metadata changes. A scoped guard on changes to the actual indexed fields is therefore a strong task-2 candidate that can preserve fresh read timestamps, returned counts and events. It must retain index correctness for genuine title/body changes and coexist with FTS repair. This trigger-only proposal is not implemented or measured as an after-state here.

In contrast, exact same-value vault/bridge writes have **zero** page writebacks in this fixture. Advancing timestamps produces **30 page writebacks / 30 vault touches** and **120 / 120 heartbeat saves**. Already-read conversation calls with advancing timestamps produce **100 page writebacks / 20 calls**, versus 80 with a fixed clock. This is why blanket timestamp suppression is not recommended, and why SQL statement counts alone cannot justify a disk-write claim. Individual cache-write counts also depend on FTS segment/checkpoint state within this deterministic replay; they are not a universal per-row constant.

A conditional SQL UPSERT/UPDATE guard may reduce page writes while still executing one DML statement per call. A service-level skip may remove the statement but introduce a read/race; measure both statement and page-write counters rather than assuming either approach removes all reported executions.

### Advancing-clock WAL and serialization evidence

Vault uses a 4s pending-device refresh interval, conditional on a valid signer; approved-device polling stops. Heartbeats use the default 45s interval. Injected time advances without sleeping, so these runs measure work rather than elapsed latency. Before each scenario, the harness checkpoints/truncates its disposable WAL; afterward `PRAGMA wal_checkpoint(PASSIVE)` reports **30 vault frames** and **120 heartbeat frames**. Probes run outside snapshots. No other writer runs, and these batches remain below automatic checkpoint thresholds. WAL frames are SQLite log records, not fsyncs or physical-device writes.

Existing `heimdall_db_lock_wait_seconds_count` observations count acquisitions including uncontended ones: vault **90 conn_vault + 30 vault mutex**, heartbeat **720 conn_main**. These include prepare/step/finalize serialization; they are not SQLite writer-lock counts. The vault mutex protects its dedicated writer; bridge repository calls serialize on main without a separate instrumented bridge mutex. The single-thread fixture does not measure production waiting. Each standalone successful DML uses autocommit: **30 vault writer transactions**, **120 bridge writer transactions**, inferred from the real code path. Both have **zero explicit BEGIN/COMMIT statements**; implicit transactions still acquire writer locks and commit. There is no direct SQLite writer-lock counter here. A SQL value guard can avoid dirty pages yet retain transaction/connection work; a safe service-level skip may remove both.
