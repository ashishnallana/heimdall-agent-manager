# Desktop automatic updates: implementation design

Extend the existing `electron-updater` integration with visible status, authenticated native controls, explicit restart consent, and a signed-release eligibility gate. Keep the existing GitHub Releases host, electron-builder, NSIS installer, and signed macOS ZIP format. Linux, Nix, development builds, and unsigned Windows builds must display an explanation and never self-modify. This is a design and implementation acceptance contract, not a claim that signed Windows updates or native end-to-end updates have been verified.

## Requirements and implementation acceptance

### REQ-AU-1 — eligibility and immutable installations

Return a structured capability with `supported`, `reason`, `currentVersion`, and platform/distribution. Initialize without network access when unsupported. Runtime policy is enforced in main, not trusted from UI.

| Distribution | Policy |
| --- | --- |
| macOS ARM64 installed signed Ninjy.app, from DMG or app component of PKG | Eligible for signed ZIP app update. Reject mounted DMG, read-only/managed location and `/nix/store` paths with reinstall/package-manager guidance. PKG receipts and installed Bridge are outside app update scope. |
| macOS Intel x64 | Same policy, but only releases that actually include x64 ZIP are usable. Missing architecture is a clear unavailable/error state; never substitute ARM64 or silently claim current. Intel release remains opt-in. |
| Windows x64 NSIS installed app | Eligible only when packaged release policy includes a nonempty configured publisher and signature verification enabled. Same installer identity/app ID/install location; preserve app-only update switches. |
| Existing unsigned Windows release | `disabled`, reason `signing-unavailable`, with official release link/manual reinstall guidance. No download/install API path may bypass eligibility. Existing old app binaries cannot be retroactively secured; users bootstrap the first signed version manually. |
| Windows portable, Store/MSIX, unpacked distribution; unknown architecture | Explicit unsupported state. No Squirrel.Windows/MSIX migration. |
| Linux including AppImage/deb; Nix on any platform | Explicit package-management/manual-install state and no updater network/download/install. This deliberately removes existing AppImage self-update eligibility. Never chmod, copy over, or replace `/nix/store` contents or package-managed installs. |
| Development/unpackaged builds | Disabled. Never set `forceDevUpdateConfig`; use injected fake updater in tests. |

Distribution eligibility must use a build-owned policy marker (proposed `resources/desktop-update-policy.json`) plus packaged updater configuration, not `APPIMAGE` or `isPackaged` alone. Generate that marker as part of signed desktop packaging; missing, malformed or mismatched policy disables updates. Its fixed schema is `{ schemaVersion: 1, distribution: 'mac-app' | 'windows-nsis', updatesEnabled: boolean, publisherName?: string[] }`; no URLs, tokens, executable paths, or renderer-supplied overrides. On Windows, compare its publisher list to generated `app-update.yml` and reject `verifyUpdateCodeSignature: false` or missing publisher metadata. Merely removing the current false flag is insufficient: inspected 6.8.12 `NsisUpdater.verifySignature()` returns success when publisher metadata is absent.

### REQ-AU-2 — retain packaging, feed and version identity

Keep `electron-updater` 6.8.12 and builder 26.18.0. Use generated `resources/app-update.yml`; never call `setFeedURL` from renderer input or ship GitHub credentials. Keep GitHub HTTPS public release hosting and permissions `contents: read` in build jobs, `contents: write` only for deliberate publication. No additional update service or production deployment.

Required feed contract:

| Platform | Metadata and payload |
| --- | --- |
| Windows x64 | `latest.yml`, `Ninjy-VERSION-x64.exe`, matching `.exe.blockmap`; manifest `version`, `files[].url/sha512/size`, legacy `path/sha512`, `releaseDate`. Signed NSIS EXE, not Bridge bundle ZIP. |
| macOS ARM64/x64 | `latest-mac.yml` containing matching architecture-specific `Ninjy-VERSION-ARCH.zip` entries, matching SHA-512/size and release version; ZIP blockmaps retained. DMG/PKG remain manual-install assets. Merge after both jobs when Intel is enabled; ARM64-only releases are explicit. |

Validate final payload existence, digest, size, architecture and manifest version before release upload and again before promotion. Do not assume `SHA256SUMS` authenticates manifests or all desktop payloads. It currently serves the Bridge distribution path; updater SHA-512 is separate. Extend `promote-release.yml` to require the desktop feed/payload set appropriate to each advertised platform and enabled architecture and reject incomplete candidates. Promotion must keep bytes unchanged. Use native `app.getVersion()` for UI/current-version comparisons, never Hub/UI version or source package version.

### REQ-AU-3 — stable and candidate behavior

Phase one is stable-only: explicitly set `allowPrerelease=false`, `allowDowngrade=false`, and use default/latest channel, including when the installed app itself is a candidate. No beta toggle or custom channel setting is exposed. Existing numerically versioned candidates (GitHub prerelease flag true, e.g. v0.5.33) are invisible to normal checks until promotion. Installing a newer candidate manually must not downgrade to the older stable. A candidate becomes discoverable after clearing prerelease and marking Latest, without changing the application version or rebuilding assets.

Semver-suffixed alpha/beta releases are not an enabled desktop channel in this increment. Existing pipeline assumes `latest*.yml`; document/reject unsupported suffix publication for desktop rather than pretending it creates a working beta feed. Supporting such channels later requires explicit GitHub channel configuration and tests, not simply setting `allowPrerelease=true`.

### REQ-AU-4 — signed integrity and release prerequisites

SHA-512 detects altered payloads relative to metadata; HTTPS/GitHub account control protects feed transport. An unsigned digest from the same host is not publisher authentication. macOS must retain Squirrel signature validation and same trusted Developer ID/team/app identity. Keep hardened runtime, entitlements, notarize/staple before ZIP packaging and verification of final signed artifacts. Require native `codesign --verify --deep --strict`, Gatekeeper assessment, and notarization ticket validation in release validation. Verify staged Bridge binaries as existing CI does.

Windows must enable signature validation, configure the expected Authenticode publisher, and require valid signatures from that publisher on full NSIS installers. Set the pinned updater's `disableWebInstaller=true` to reject web-installer paths. No custom verifier returning success, unsigned fallback, or trust-on-first-download. Signed distribution CI must fail closed when required credentials/publisher are missing; unsigned manual builds may remain possible but their policy marker must disable updater. Use conditional signed-release packaging and `forceCodeSigning` for that path, and verify the built EXE with native Authenticode tooling before upload. Do not create keys or guess a publisher.

Known source-referenced secret names only: `MACOS_DEVELOPER_ID_P12_BASE64`, `MACOS_DEVELOPER_ID_P12_PASSWORD`, optional `MACOS_DEVELOPER_ID_INSTALLER_P12_BASE64`, `MACOS_DEVELOPER_ID_INSTALLER_P12_PASSWORD`, `APPLE_ID`, `APPLE_APP_SPECIFIC_PASSWORD`, `APPLE_TEAM_ID`. Workflow maps imported app identity to `HEIMDALL_MACOS_CODESIGN_IDENTITY` and `CSC_NAME`; optional installer identity is for PKG signing. Windows has no configured signing inputs. Proposed external setup: operator supplies a public trusted Windows signing identity, exact publisher name, and supported signing access; for certificate-based builder signing, map CI secrets `WIN_CSC_LINK` and `WIN_CSC_KEY_PASSWORD` to builder `CSC_LINK` and `CSC_KEY_PASSWORD`, with a reviewed non-secret publisher configuration. Hardware/cloud signing may require another provider and must be confirmed by operator, not invented in code.

`gh secret list` could not run because `gh` is absent; unauthenticated GitHub `/actions/secrets` returned 401. Secret presence, expiration, permissions, and suitability are unverified. Existing public macOS artifacts suggest prior packaging success but do not prove credentials remain available. Therefore the current pipeline can build unsigned Windows manual installers, but cannot produce the required authenticated Windows auto-update chain without external signing setup. macOS release builds already fail when signing/notarization inputs are absent. No claim of working native releases until signed N→N+1 smoke tests pass.

### REQ-AU-5 — state machine, scheduling, progress and retry

Keep startup delay 30 seconds and interval six hours, only after app ready and eligible. Store both timeout and interval handles; clear both on stop, detach listeners and prevent late async events from publishing after disposal. Use one check/download flight, skip background checks during checking/downloading/downloaded/restart preparation, and make repeated manual clicks return current state. Do not overwrite a ready cached update with a scheduled check. Test start/stop/restart idempotence.

State phases: `disabled`, `idle`, `checking`, `available`, `downloading`, `downloaded`, `up-to-date`, `error`, `preparing-restart`. Snapshot includes schema version, current/target versions, eligibility reason, bounded sanitized message/error code, finite clamped percent, transferred/total bytes where valid, last check time and retryability. Throttle progress publications (e.g. 250 ms); publish terminal events immediately. Treat bad numeric progress as unknown, not NaN.

Automatic download is retained for eligible signed builds. Do not auto-install on normal quit: set `autoInstallOnAppQuit=false` before checks. Manual Retry rechecks metadata then redownloads through the library, preserving its checksum and signature validation, and never uses a cached unverified path. No unbounded short retry loop; automatic recovery is next six-hour check and user can retry immediately. Offline, rate limit, missing feed/architecture, digest mismatch, signature failure and disk errors get distinct safe diagnostics; signature failures never enable restart. Log technical details in native logs without credentials or rendering raw server HTML. User can keep using the current app on every failure.

No arbitrary channel dispatch, paths, feed URLs, version/publisher setters or shell execution. Main owns confirmation, eligibility, downloaded-state and busy-state checks. Register all invoke handlers through existing trusted main-window/top-frame/origin guard (rename `bridgeHandler` to a generic native guard if helpful, preserving tests). Send state only to the trusted current main window and snapshot after load/navigation; a destroyed window cannot break updater operation. Ignore/reject foreign subframes, OIDC popups and nonmatching origin. UI receives data, never installer bytes or credentials.

In `src/ui/bridge/desktopBridge.ts`, add complete method/schema capability detection with `null` for absent/legacy updater APIs. Old native versions must see manual upgrade guidance, not dead buttons. Browser UI must not imply local update support. Extend `src/vite-env.d.ts` only as needed to align types.

Add `src/ui/components/settings/DesktopUpdatesPanel.tsx` and wire an App updates category in `src/ui/components/settings/SettingsModal.tsx` and `src/ui/utils/settingsRouting.ts`. Show installed version, eligibility reason, stable-channel label, last check, progress, Retry, Check for updates, Restart to update and Later. A native application menu entry in `main.cts` checks through the same controller and provides native dialogs so updates remain actionable if a Hub serves an older/offline UI. Download completion produces a non-blocking native notice/dialog with Later as safe default; never a forced modal on every progress event. Reopening settings refreshes snapshot then subscribes, and disposes subscriptions on close.

Required stable IDs: `settings-nav-updates`, `desktop-updates-panel`, `desktop-updates-current-version`, `desktop-updates-status`, `desktop-updates-check`, `desktop-updates-progress`, `desktop-updates-retry`, `desktop-updates-restart`, `desktop-updates-later`, `desktop-updates-release-link`. Add IDs to AGENTS.md's inventory. Status uses an accessible live region; progress uses semantic progress attributes. Native dialogs have accessible button labels; no DOM IDs are possible there.

### REQ-AU-7 — consent, work preservation and native lifecycle

Only explicit Restart to update followed by a native confirmation may authorize installation: Windows uses `quitAndInstall(false, true)`; macOS uses the gated native adapter specified below. Before explicit restart consent, Later, closing settings, ordinary app quit, OS logout, background timers and wrapper update-download events never initiate native staging or installation. After consent has initiated macOS native staging, abort guarantees and native limitations are specified below. Reject duplicate restart requests. Confirmation states the window will restart and Bridge agents continue independently; never stop/reinstall the service to update the app.

Before confirmation/install, coordinate renderer preparation through a main-generated request ID: ask only the trusted main frame to flush current composer drafts, layout and pending local edits; require bounded success acknowledgement from that frame/request. Recheck eligibility, ready version, and Bridge operation state after await. If renderer is unavailable, persistence throws, an edit/upload/send is unresolved, or a Bridge install/enrollment/update/uninstall operation is running, refuse restart with actionable message; do not force after timeout, cancel work or rely on the existing bounded quit cancellation. An offline Hub does not matter if already-loaded renderer preparation succeeds; an unavailable renderer means Later/manual restart until it is ready.

Implement a small renderer preparation registry in proposed `src/ui/utils/desktopUpdatePreparation.ts`. Register persistence flush/blocker callbacks at `AgentChatPane.tsx` and `Workspace.tsx` and relevant pending editor/upload boundaries; reuse current persistence keys. Preparation must observe storage failure (add checked variants rather than assume current swallowing helpers succeeded). Do not serialize vault secrets/new drafts into logs or introduce unrelated persistence architecture. Tests must prove latest keystroke and layout survive; if any unsaved surface cannot safely flush, it must block with a save/discard instruction. Never report all work preserved solely because one composer was persisted.

#### Preparation is a held transaction, not a one-time acknowledgement

Main creates a monotonically increasing restart epoch bound to the current window/webContents, main-frame document/navigation identity, target version and preparation request. Acquire the Bridge-operation exclusion before preparation. Renderer enters a visible frozen state **before** flushing: block composer/editor changes, send/upload actions, layout mutations, navigation and new pending work at their mutation/dispatch boundaries, not just by disabling the settings button. Register every unsaved surface; missing coverage blocks restart. After checked flushes and all blockers resolve, acknowledge that epoch while retaining the freeze. Main displays confirmation only after that acknowledgement; the freeze and Bridge exclusion remain held throughout confirmation, delayed native staging and final exit. There is no editable interval after acknowledgement. Required overlay IDs: `desktop-update-preparing-overlay`, `desktop-update-preparing-status`; register them in AGENTS.md.

Immediately before any installer/quit call, synchronously validate the epoch, same live trusted document, eligibility, target, held freeze and Bridge exclusion. Renderer navigation/reload/crash/destruction, changed target, lost freeze, new blocker, timeout or native error invalidates the epoch and disarms the exit path first. Main cancels the transaction and then sends an epoch-specific release; renderer ignores stale releases/acks. Main must also intercept navigation and window close while preparing; an unexpected navigation attempt aborts rather than treating an old acknowledgement as valid. A successful final gate keeps the renderer frozen until process exit. An aborted transaction restores editing and operation availability, with explicit error state. Beforeunload veto must abort and release the transaction, never leave the app stuck.

#### macOS staging and disarming contract

Exact 6.8.12 `MacUpdater.js` dispatches wrapper `update-downloaded` when the cached ZIP/proxy feed is ready. With `autoInstallOnAppQuit=false`, Squirrel download/signature verification is deferred. Its `quitAndInstall()` registers a persistent native `update-downloaded` listener invoking `handleUpdateDownloaded()`; native error does not remove it. Therefore **do not call the library macOS quitAndInstall method at all**, including on retry. Merely resetting application busy state or removing application listeners cannot disarm that library callback.

Implement proposed `src/ui/electron/macUpdateInstall.cts` as a narrow, injectable adapter around Electron public `autoUpdater`. Retain electron-updater for trusted download, architecture selection, SHA-512 and its generated loopback feed. After cached wrapper completion and held preparation/consent, attach owned native completion/error handlers, then call Electron `autoUpdater.checkForUpdates()` to stage from that already-configured feed. Do not override feed URLs or use private MacUpdater fields. Its constructor listeners only record native completion/forward error; neither quits. The adapter is the sole code allowed to invoke native `autoUpdater.quitAndInstall()`, synchronously after native signature-validated completion and the final epoch/freeze gate. Never install in response to the wrapper download event. Keep `autoInstallOnAppQuit=false` throughout.

Disarm by invalidating the epoch **before** detaching owned listeners and releasing the freeze. Native callbacks must test both their captured epoch and an active one-shot install authorization; consume authorization before the quit call. On native error, staging timeout (bounded, proposed 120 seconds), renderer invalidation, cancellation or disposal, remove owned completion/error listeners and timers. Never use `removeAllListeners`, which would disturb Electron/library handlers. Catch synchronous native failures too. A late native completion then has no path to quit, even if the library records its downloaded flag.

Native events carry no attempt ID and staging cancellation is not a documented guarantee. Consequently permit only one native staging attempt per process. After any aborted/failed staging, mark the adapter quarantined until app relaunch; Retry cannot rearm staging or installation in that process and must show relaunch/manual-update guidance. Metadata/download retry before native staging remains allowed. This prevents a late completion from failed attempt A authorizing attempt B. Do not claim abort undoes native staging or guarantees that Squirrel will discard an already staged update on an eventual user-initiated ordinary exit; verify that platform behavior in native acceptance and report it. Product guarantees are no application-triggered quit from an invalid transaction and no background staging before explicit restart consent. If native testing shows a stronger no-install-after-abort requirement is needed, block rollout and resolve it rather than claiming unsupported cancellation.

Windows verifies the installer during download; use its library install only after the same held preparation and final gate, before windows can close. Retain ordinary-quit Bridge cleanup and notification disposal. Restart cannot cancel a running Bridge operation. Native installer failure or beforeunload veto releases guards and reports error. Next successful launch reports `app.getVersion()`; never optimistically change installed version.

Required focused lifecycle tests use controllable delayed native staging: latest edit immediately before freeze persists; edit/send/upload/layout mutation after acknowledgement is rejected; navigation/reload/crash invalidates authorization; Bridge starts are rejected while held; completion with valid epoch exits once; cancellation/error/timeout before completion releases freeze; error then late completion never quits; Retry after failed staging remains quarantined; duplicate/late events and stale release/ack cannot trigger exit or unlock a newer transaction. Inspect the exact pinned MacUpdater integration in a test to prove its persistent quit listener is never registered by our path. Native macOS acceptance must delay staging while attempting edits/navigation and inject a failure followed by completion. These are acceptance requirements, not tests claimed executed by this design task.

## External constraints and handoff definition of done

Implementation may proceed now with Windows updater disabled until operator-provisioned signing is available. No user permission is needed to add reversible local code/design/tests within the assigned task. Missing credentials do not justify weakening verification. Report application implementation readiness separately from per-platform release readiness; leave Windows signed-release validation explicitly incomplete if inputs are unavailable. A signing identity or installation distribution policy discovered to conflict with this design goes to the coordinator before broadening scope.

Done means all REQ-AU-1 through REQ-AU-7 have code and focused behavioral evidence; updater is usable through native menu and current UI; ineligible installs cannot invoke it; release validators require complete matching artifacts; signer requirements and unsigned bootstrap are documented; restart consent and preservation invariants have direct tests. Native signed rollout readiness additionally needs the native N→N+1 evidence above. Commit the implementation and report exact checks, skips, platform constraints, paths and commit to independent review. Do not merge/deploy/publish as part of implementation.
